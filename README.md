# SecuRDP

One program, `securdp.exe`, that is both:

- **the gatekeeper** on the PC you want to reach. It runs as a Windows service on one port that you open on your router.
- **the client** on the PC you connect from. It logs in, opens the tunnel and launches Remote Desktop through it.

```
Laptop                                      Router                 Home PC
mstsc → 127.0.0.x:13389 ─┐
                         └── SSH (encrypted) ──► TCP <gate port> ──► SecuRDP service
                             password + Google                       │ only ever forwards to
                             Authenticator code                      ▼ 127.0.0.1:<RDP port>
                                                                   Windows Remote Desktop
```

## Security design

| Threat | Protection |
|---|---|
| Password guessing | Password (14+ chars, Argon2id-hashed) **plus** a 6-digit Google Authenticator code. Failed attempts ban the source IP (5 tries → 30 min, doubling each repeat, up to 24 h). Every failure adds a 1 s delay. |
| Username guessing | Common names (admin, root, …) are refused. A wrong username takes the same time to reject as a wrong password, so valid usernames can't be discovered. |
| Using the port to reach other machines | After login, the **only** thing allowed is a tunnel to this PC's own RDP port. No shell, no file transfer, no remote forwarding, no other destinations, whatever the client asks for. |
| Eavesdropping | SSH with modern algorithms only: post-quantum ML-KEM/X25519 key exchange, ChaCha20-Poly1305 / AES-GCM. RDP's own TLS runs inside that, so traffic is encrypted twice. |
| Fake server / man-in-the-middle | The client pins the server's key fingerprint on first connect, and refuses to connect if it ever changes. |
| Reusing a code someone saw | Each authenticator code works once. |
| Direct RDP exposure | Optional firewall rule blocks the real RDP port from **internet** addresses. Your home network (10.x, 172.16-31.x, 192.168.x) and Tailscale/CGNAT (100.64/10) can still RDP in directly, and outgoing RDP is never affected. Tunnelled traffic arrives on loopback, so SecuRDP keeps working. **Never forward 3389 on your router.** |
| Forgotten sessions | An open Remote Desktop session is never cut. After the last RDP connection closes, the tunnel stays open for a grace period (default 5 min, so a quick reconnect works) and then closes. |
| Stolen config file | `C:\ProgramData\SecuRDP` is readable only by SYSTEM/Administrators. Authenticator secrets are also encrypted with Windows DPAPI, tied to that PC. |
| Slow-connection floods | 45 s login deadline, max 3 pending logins per IP, a cap on sessions, keepalives to drop dead clients. |

## Build

Requires Go 1.26+.

```powershell
.\build.ps1
```

This produces `securdp.exe`. Copy that one file to any PC.

The icon, manifest and version info are generated by `tools/mkres` into `rsrc_windows_amd64.syso`, which `go build` links in automatically. The icon is drawn in code (`tools/mkres/icon.go`); edit it there and re-run `build.ps1`.

**Upgrading from "SecureRDP".** Running the new exe as administrator migrates an old install automatically: the old service and firewall rules are removed, `C:\ProgramData\SecureRDP` moves to `C:\ProgramData\SecuRDP`, and the service is reinstalled under the new name. Saved computers move from `%APPDATA%\SecureRDP` too. Users, passwords, authenticator setups and the server fingerprint are all kept. Existing Google Authenticator entries keep their old "SecureRDP" label but keep working.

## Set up the PC you connect *to* (the server)

1. Run `securdp.exe`. Go to **This PC (server)** → **Restart as administrator**.
2. **Remote Desktop**: click *Enable Remote Desktop (with NLA)* if it shows disabled or NLA off.
3. **Gate settings**: click **Random** to pick a port (e.g. 47213), then **Save settings**.
4. **Users & Authenticator** → **Add user** (see the Google Authenticator section below).
5. **This PC** → **Install / update service**. This copies the exe to `C:\Program Files\SecuRDP`, registers an auto-start service and adds the firewall rule.
6. On your **router**, add a port forward: TCP, external port = gate port → this PC's LAN IP (shown on the page), same internal port.
7. Write down the **server fingerprint** shown at the bottom of the page.

> **Your public IP can change.** Your ISP may change your home IP. A free dynamic DNS name (many routers support DuckDNS, No-IP, etc.) gives you a stable hostname to put in the client.

## Setting up Google Authenticator

You're used to scanning a QR code a website shows you. Here **SecuRDP is the website**: it creates the secret and shows the QR code.

1. In **Users & Authenticator** click **Add user**, choose a username and a strong password, and click **Next**.
2. A QR code appears. On your phone open **Google Authenticator** → tap **+** → **Scan a QR code** → scan it.
3. A new entry **SecuRDP (yourname@PCNAME)** appears with a 6-digit code that changes every 30 seconds.
4. Type the current code into SecuRDP and click **Confirm**. This proves the phone and PC agree, and only then is the user saved.

Tips:
- Can't scan? Use **Enter a setup key** in the app, type the key shown under the QR code, and choose *Time based*.
- Codes depend on the clock. Keep "Set time automatically" on for both the PC and the phone.
- The QR code is shown **only once**. Anyone who sees it can generate your codes, so don't screenshot it. Lost your phone? Use **Reset password / authenticator** for that user on the server.
- Google Authenticator's cloud backup (signed into your Google account) means a new phone gets your codes back.
- Using SecuRDP on two server PCs? Each one gets its own entry in the app, labelled with the PC name.

## Connect from another computer (the client)

1. Copy `securdp.exe` there and run it. No install and no admin rights needed.
2. **Connect** tab → **Add computer**: a name, the public IP / hostname, the gate port, your SecuRDP username and optionally your Windows username on that PC. Add one entry per PC you use.
3. Click **Connect…**, then enter your password and the current authenticator code.
4. The first time, compare the fingerprint with the one you wrote down, then confirm.
5. Remote Desktop opens. Tick **Remember me** in its login box if you want Windows to save that PC's login. Each saved computer uses its own local address (`127.0.0.10`, `127.0.0.11`, …), so the saved logins never mix.
6. Close Remote Desktop and the tunnel closes.

The first time, Remote Desktop may warn that the certificate name doesn't match, because it sees `127.0.0.x`. That's expected through a tunnel. Tick *Don't ask me again* for that computer.

### Updating from the hub (1.8+)

Update the hub once (*Install / update* with the new exe). When a 1.8+ app logs in to a hub running a newer version, a banner offers **Update & restart**:
- The app downloads the hub's own `securdp.exe` through the tunnel. Behind it are the pinned host key and your password + code. The download's size and SHA-256 are checked, and the app test-runs the new file to confirm its version.
- The running exe is renamed to `securdp.exe.old`, and the new one takes its place and restarts. The old file is deleted on the next start, and open connections close.
- If you're running the **installed copy** (Program Files), or its folder isn't writable, the new version is saved to *Downloads* and opened from there instead. Use **Install / update** in it to update the service on that PC too.
- Older apps don't see the offer. Copy the new exe over once, and from then on updates come from the hub. The hub's log records each download (`UPDATE … downloaded SecuRDP x.y.z`).

**Android (1.9+):** `build.ps1` bundles the release APK into the exe, so a hub always carries the matching Android app. When a phone logs in to a hub with a newer app, the hub screen shows **Download & install**:
- The app downloads through the tunnel with its size and SHA-256 checked.
- It installs through Android's own installer, which asks you to confirm. The first time, it also asks you to let SecuRDP install apps.
- Android only accepts the update if it's signed with the same key as the installed app.
- Phones on 1.7 or older need this version installed by hand once.

### Command line

```
securdp connect "Office PC"                    # saved profile
securdp connect home.example.net 47213 myuser  # ad hoc
securdp status | install | uninstall | serve
```

Any standard SSH client works as well, e.g. `ssh -N -L 13389:127.0.0.1:3389 -p 47213 myuser@home.example.net`, then RDP to `127.0.0.1:13389`.

## Hub mode: one front door for several PCs

On an always-on PC (e.g. the Plex server), choose **Hub** under *This PC → What should this PC do?*:

```
client ──SSH──► router :port ──► hub (SecuRDP) ──► desktop 192.168.1.50:3389
                                     login + code  ├─► laptop  192.168.1.93:3389
                                     allow-list    └─► …
```

- **Computers tab:** add each PC with a name, its home-network address and, optionally, its MAC address for Wake-on-LAN. **Test** checks that Remote Desktop answers. Only these addresses can ever be reached through the hub.
- **Picking a PC:** connect with your plain username, and the Windows and Android apps (1.4+) show a list of the computers you may reach, with green dots for those answering right now. Tick *Always use this computer* to skip the list for that saved entry, or set *Hub computer* under Edit. Each PC gets its own local tunnel address, so Remote Desktop's saved logins stay separate.
- **Without the picker:** log in as `username+name` (e.g. `alex+desktop`) to go straight to a PC. A plain username in older apps goes to the default computer.
- **Users tab:** each user can reach *All computers*, or only the ones ticked.
- **The PCs behind the hub** only need Remote Desktop with NLA, reachable from the hub. The "block RDP from the internet" rule already allows home-network addresses. They don't need SecuRDP installed or a port forward.
- **Wake-on-LAN:** if a PC with a MAC address doesn't answer at login, the hub sends a wake-up packet. Reconnect after it boots.
- **Server mode** behaves exactly as before, with only this PC reachable. Switching modes needs no service restart.

### Files & home web pages (1.5+)

On the server/hub, the **Files & Web** tab sets up two things:
- **Shared folders.** Pick a name and a folder on the hub PC. Folders are read-only unless you tick *Allow uploads, new folders, rename and delete*.
- **Home web pages.** A name and an address, e.g. `router` → `http://192.168.1.254` or `plex` → `http://127.0.0.1:32400/web`. **Test** checks it answers.

Nothing is visible to anyone until you tick it for them on the **Users** tab.

In the apps, after logging in to the hub, the hub screen shows **Remote Desktop**, **Files** and **Web pages**:
- **File browser:** *Large icons* (thumbnails for photos and videos, made on the hub by Windows' own thumbnail engine), *List* or *Details* (sortable name / date / type / size).
  - **Windows:** click to open a folder; click a file for Open / Download (right-click also offers Rename / Delete in writable folders). Upload and New folder appear in writable folders.
  - **Android:** tap a file for Open / Save to phone / Share, plus Rename / Delete in writable folders.
- **Web pages** open in a SecuRDP browser window (Windows) or in the app (Android), through the tunnel. Self-signed certificates (typical for routers) ask once before continuing.
  - **Windows window (1.9.1+):** the right-click menu (Copy, Paste, Save image…) and F12 / Inspect work as in Edge. Ctrl+C / Ctrl+V work too.
  - **Open in browser / Open in Chrome ↗** hands the page to your normal browser through the same tunnel. Useful for pages with downloads, pop-ups or new tabs. It stays connected until you tap **Stop** on the hub screen, or disconnect.
  - **Android in-app browser:**
    - Pages that open a "new window" open in the same view (Back returns).
    - Downloads are saved to `Downloads/SecuRDP`.
    - Links a page builds with its *real* home address (common for full-size images) are routed back through the tunnel; 1.6+ hubs tell the app that address.
    - Links to other home-network addresses explain why they can't open, and internet links open in your browser.
    - Fullscreen (image viewers, videos) is supported; Back leaves it.
    - **⋮ → Page debugging (USB)** lets `chrome://inspect` on a USB-connected PC show the page's console and network requests (off by default). Page console messages also go to `adb logcat -s SecuRDPWeb`.

Security:
- Paths can never leave a shared folder. `..`, junctions or symlinks pointing outside, Windows device names and alternate data streams are all refused.
- Deletes are limited to files and empty folders, and uploads never overwrite.
- Every file action is written to the activity log (`FILE user=… get "media/…"`).
- Users without a grant get nothing, even if their app asks directly.

### App links (1.7+, Android)

An app link lets another app on your phone, such as one that runs in the background, reach **one** hub web page at `127.0.0.1:<port>` without your password or authenticator code.

1. **On the hub**, add the page under *Files & Web* (e.g. `http://127.0.0.1:11435`), tick it for the user, and tick **App links** for that user on the *Users* tab.
2. **On the phone**, connect to the hub normally (password + code). Under **App links**, tap **Link an app to …**, name the phone and pick the port (it defaults to the page's own port). Then tap **Pair**.
3. The link appears on the app's main screen with an on/off switch. A quiet "App link ready" notification keeps the port listening, and the link restarts after a reboot.

How it works and what it can't do:
- Pairing creates an ECDSA P-256 key in the phone's **Android Keystore**, which can't be exported. Only the public key is sent to the hub, over the logged-in session.
- A key login can reach **only its own page**. Remote Desktop, files, the computer list, other pages and pairing are all refused and logged.
- The SSH connection opens only when an app connects, and closes a minute after the last connection ends. When the network changes, the next request simply logs in again.
- **To revoke:** tap **Remove** on the phone (also removed on the hub if you're connected), or tap **Remove** next to the device on the hub's *Users* tab. Removing the page, ungranting it, or turning App links off for the user also stops the link. Unknown keys are logged but don't count towards IP bans.
- Every app on the phone can reach a loopback port, so the page should check its own token. The link controls who reaches the hub, not which app on the phone uses it.

### Dynamic DNS (DuckDNS)

*This PC → 5. Dynamic DNS*: sign in at duckdns.org, add a name, then paste the name and token. The service checks your public IP every 5 minutes and updates DuckDNS when it changes, plus a daily refresh. Clients then use `name.duckdns.org:port`. The token is stored encrypted, and DDNS events appear in the activity log.

## Android app

`android/` is a native Kotlin app that does the same job as the Windows client. It keeps saved computers, asks for your password and authenticator code each time, pins the server fingerprint, and holds the encrypted tunnel in a foreground service with a **Disconnect** notification. It then opens Microsoft's **Windows App** at the tunnel (`127.0.0.1:13389`, a different port for each saved computer). The tunnel closes 2 minutes after the last Remote Desktop connection ends.

Build it (Android Studio's SDK, JDK 17+):

```powershell
cd android
.\gradlew.bat assembleRelease      # -> app\build\outputs\apk\release\app-release.apk
```

Release signing uses `android/securdp-release.jks` with its passwords in `android/keystore.properties`. Both are excluded from git. **Back them up.** Updates to the installed app must be signed with the same key; otherwise you'll have to uninstall and reinstall.

Tests: `.\gradlew.bat testDebugUnitTest` does a real handshake with the local SecuRDP service, stopping before login. For a full login and tunnel test, first start the throwaway gate: `SECURDP_SERVE_ADDR=127.0.0.1:38999 go test ./internal/server -run TestServeForExternalClient`. Then add `-Dsecurdp.e2e.port=38999` to the Gradle test command.

## Files

| Path | What |
|---|---|
| `C:\Program Files\SecuRDP\securdp.exe` | installed service binary |
| `C:\ProgramData\SecuRDP\server.json` | server settings and users (admin-only) |
| `C:\ProgramData\SecuRDP\hostkey` | server identity key (admin-only) |
| `C:\ProgramData\SecuRDP\securdp.log` | logins, failures, bans (also on the *Activity log* tab) |
| `%APPDATA%\SecuRDP\client.json` | saved computers on the client |

## Tests

```powershell
go test ./...
```

The tests cover the RFC 6238 TOTP vectors and a full login → tunnel → RDP round trip. They also check unknown-server detection, rejection of replayed codes, wrong passwords and wrong codes, and refusal of shells and remote forwarding, plus IP banning and the UI's API token check.
